# Technical Guide: System Architecture Overview

## Overview
This guide provides an overview of the system architecture for our platform, including key components, data flows, and integration patterns.

## System Components

### Frontend Layer
- **Web Application**: React 18 with TypeScript, Next.js 14 App Router
- **State Management**: TanStack Query for server state, React Context for client state
- **Styling**: Tailwind CSS with shadcn/ui component library
- **Build Tool**: Turborepo for monorepo management

### API Gateway
- **Technology**: Kong API Gateway
- **Authentication**: JWT validation, OAuth 2.0 / OIDC integration
- **Rate Limiting**: Token bucket algorithm, configurable per client
- **SSL Termination**: TLS 1.3 at gateway level

### Backend Services
- **User Service**: Go 1.21, gRPC/REST, PostgreSQL backend
- **Document Service**: Python 3.11, FastAPI, PostgreSQL + Qdrant
- **Search Service**: Rust, Tantivy index, gRPC interface
- **Notification Service**: Node.js 20, NATS messaging, multi-channel (email, push, SMS)

### Data Layer
- **Primary Database**: PostgreSQL 16 with logical replication
- **Vector Database**: Qdrant 1.10 for embeddings and similarity search
- **Cache**: Redis 7 Cluster for session and query caching
- **Message Queue**: NATS JetStream for event streaming
- **Object Storage**: MinIO (S3-compatible) for document storage

## Data Flows

### Document Ingestion Pipeline
1. Client uploads document via REST API
2. API Gateway validates and routes to Document Service
2. Document Service extracts text and metadata
3. Text is chunked using configurable strategies
4. Embeddings generated via configured provider
5. Vectors stored in Qdrant, metadata in PostgreSQL
6. Ingestion job status updated in real-time

### Query Processing
1. User submits query via Chat API
2. Query embedded using same embedding model
3. Vector similarity search in Qdrant
3. Retrieved chunks validated and filtered
4. Context constructed with citations
5. Generation provider generates grounded answer
6. Citations validated against retrieved chunks
7. Response returned with citations and metadata

### Evaluation Pipeline
1. Evaluation job created with dataset and configuration
2. For each sample: retrieve, generate, validate citations
3. Deterministic metrics computed (Precision@k, Recall@k, MRR, nDCG)
4. Optional judge-based evaluation (Ragas, custom)
5. Results aggregated and stored with full traceability

## Configuration Management

### Environment Variables
All configuration via environment variables with `.env` files for local development. Secrets never committed to version control.

### Feature Flags
Feature flags managed via LaunchDarkly for gradual rollouts.

### Secrets Management
- Local: `.env` files (gitignored)
- CI/CD: GitHub Secrets
- Production: HashiCorp Vault (planned)

## Deployment Architecture

### Local Development
- Docker Compose for full stack
- Mock providers for zero-cost development
- Hot reload for frontend and backend

### Staging
- Kubernetes (k3s) on dedicated VM
- Real providers with test credentials
- Automated deployment via GitHub Actions

### Production
- Kubernetes (EKS/GKE) with multi-AZ deployment
- Blue-green deployments
- Comprehensive monitoring and alerting

## Monitoring and Observability

### Metrics
- Prometheus for metrics collection
- Grafana dashboards for visualization
- Key metrics: latency, error rate, throughput, queue depth

### Logging
- Structured JSON logging with correlation IDs
- Centralized via Loki
- Log retention: 30 days hot, 1 year cold

### Tracing
- OpenTelemetry instrumentation
- Jaeger for trace visualization
- Sampling: 10% of requests, 100% of errors

### Alerting
- PagerDuty for critical alerts
- Slack for warnings and info
- Runbooks linked in alert descriptions

## Security

### Network
- Private subnets for all services
- WAF at API Gateway
- mTLS between services (planned)

### Data Protection
- Encryption at rest (AES-256)
- Encryption in transit (TLS 1.3)
- Field-level encryption for PII (planned)

### Access Control
- RBAC with fine-grained permissions
- Just-in-time access for production
- Regular access reviews

## Disaster Recovery

### Backup Strategy
- PostgreSQL: Daily full, hourly incremental
- Qdrant: Daily snapshots
- Redis: AOF + RDB snapshots
- MinIO: Cross-region replication

### Recovery Objectives
- RPO: 1 hour (PostgreSQL), 24 hours (Qdrant)
- RTO: 4 hours (critical services), 24 hours (non-critical)

### Testing
- Monthly restore drills
- Annual full DR exercise
- Chaos engineering quarterly
